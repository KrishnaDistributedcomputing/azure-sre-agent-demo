1. Executive argument: reduce investigation friction, not accountability

Reliability incidents usually begin with an incomplete observation: requests are failing, latency has increased, or a queue is growing. The operational work is to establish scope, gather evidence from several systems, compare explanations, and choose a reversible response. Azure SRE Agent provides an agent-assisted interface to that work. Its value is not that a model can describe an outage; it is that a configured agent can retrieve relevant operational context and use permitted tools within an organization's controls.

Microsoft describes interactive investigation, incident-driven workflows, and scheduled operational work. These are different entry points into the same engineering problem: observations must become testable hypotheses before they become infrastructure changes. A useful output therefore identifies evidence, uncertainty, proposed actions, and validation criteria rather than merely presenting a plausible root cause.

This evaluation portal is a teaching surface, not the SRE Agent service. Its Functions generate bounded signals, and its public pages display selected telemetry and instructional samples. Opening a scenario does not start an agent thread. A sample chart is not a saved Live Report. A remediation recommendation is not an executed recovery.

Product grounding: Microsoft Learn: Azure SRE Agent overview [1].

2. Deployment architecture: distinguish four operational boundaries

The component command center describes the deployment topology. For reasoning about access and failure, separate the workload that produces evidence, the services that store it, the agent that investigates it, and the governance that limits its lifecycle.

How to use this architecture

  1. Run one bounded scenario and confirm its trace in the demo workspace before asking the agent to diagnose it.
  2. Verify that the agent can query that workspace and inspect the specific Function App or queue. Dashboard access alone does not establish agent access.
  3. Start a scoped investigation. Configure Azure Monitor incident intake separately if you want alert-driven investigations; no such integration is created by this figure.
BoundaryComponents in this evaluationEngineering responsibility
WorkloadLinux Azure Functions Flex Consumption, private deployment package storage, and Azure Storage QueueGenerate controlled HTTP, latency, queue, memory, CPU, configuration, and release signals. Keep each operation bounded.
EvidenceApplication Insights, Log Analytics, Azure Monitor rules, availability testing, and workbookRecord requests and scenario traces, evaluate configured alert thresholds, and provide queryable evidence.
InvestigationAn existing Azure SRE Agent, its identity, managed resource scope, and configured tools or connectorsGather authorized context, compare hypotheses, and propose or perform actions only within effective permissions and policies.
GovernanceAzure RBAC, monthly budget notifications, telemetry cap, and scheduled teardown Logic AppLimit access, monitor spend, and remove evaluation resources before unintended ongoing charges.

Provisioning is not integration

The deployment script submits subscription-scoped Bicep, configures the telemetry cap, and publishes the Python Functions application. The template references the SRE Agent resource group as existing; it does not provision the agent itself. Resource creation also does not prove that the agent has a working Log Analytics connection, an enabled incident integration, or an approved response plan. Verify those separately before presenting an automated workflow.

Do not confuse identities

The public Function App uses its own managed identity for server-side telemetry and inventory reads. The deployment identity accesses package storage. The SRE Agent has its own user-assigned managed identity and managed-resource permissions. These principals are not interchangeable: a functioning public dashboard does not prove that the agent can query the same data. Neither identity's tokens should be returned to the public browser.

3. Investigation lifecycle: from a signal to verified recovery

How to use this sequence during a scenario

For catalog latency, invoke latency, ask the agent to compare the three-second recorded wait with request P95, and require citations before accepting its diagnosis. If worker CPU is missing, the correct result is an explicit gap, not a claim of CPU saturation. After an approved real code change, repeat the same check and compare equivalent windows; the fixed-sleep simulation does not recover on its own.

  1. Establish the trigger and scope. An engineer can start a conversation, or an explicitly configured incident integration can initiate a workflow. Record resource scope, incident time, and the question being investigated.
  2. Retrieve evidence. Query requests, traces, resource properties, and available change history. Align timestamps and operation identifiers before assuming that nearby events are causally related.
  3. Compare hypotheses. Separate application faults, downstream failures, resource pressure, and recent changes. Record the evidence that would disprove each explanation.
  4. Propose a bounded response. Identify the exact resource, expected benefit, operational risk, rollback method, and approval owner. Prefer a narrow mitigation over an unexplained broad restart.
  5. Apply the effective governance controls. Resource permissions determine what is reachable; tool policies, hooks, connector controls, and run modes determine how a tool call is handled.
  6. Validate independently. Requery the failure signal, repeat an appropriate customer-facing check, and verify that recovery did not merely move the problem elsewhere.

For Azure Monitor incident intake, Microsoft documents a configured integration that scans alerts and consolidates repeated rule firings. An email Action Group alone is not that integration. Check that Azure Monitor is connected in the agent's incident-platform configuration, that the required identity permissions exist, and that a real alert fired. This portal does not verify those settings.

4. Evidence engineering: keep observations separate from labels

Each controlled scenario emits JSON into application traces with its name, severity, result status, elapsed duration where populated, item count, summary, expected root cause, and a scenario correlation ID. Workspace-based queries read these records from AppTraces; request volume and latency percentiles come from AppRequests.

The expected_root_cause field is a label supplied by the simulation author, not a conclusion independently established by the agent. Likewise, a scenario correlation ID should not be assumed to equal Application Insights OperationId. Confirm the actual linkage before joining records. A duration of zero in this trace means that the scenario did not populate an elapsed-duration measurement, not that the HTTP request took no time.

Trace-level evidence for one scenario

AppTraces
| where TimeGenerated >= ago(24h)
| where Message has '"eventType":"sre-demo-scenario"'
| extend event = parse_json(Message)
| where tostring(event.scenario) == "latency"
| project TimeGenerated,
    scenario=tostring(event.scenario),
    statusCode=toint(event.status_code),
    recordedDurationMs=toint(event.duration_ms),
    simulationLabel=tostring(event.expected_root_cause),
    correlationId=tostring(event.correlationId)
| order by TimeGenerated desc

Request latency is a different measurement

AppRequests
| where TimeGenerated >= ago(24h)
| summarize requests=count(),
    failures=countif(Success == false),
    p95RequestMs=percentile(DurationMs, 95)
    by Name, bin(TimeGenerated, 5m)
| order by TimeGenerated asc

The second query groups by operation name so a reader can distinguish scenario requests from other portal traffic. Its P95 is computed from recorded requests; it must not be populated from the first query's single-event duration. Sampling, ingestion delay, missing instrumentation, and short windows can all weaken the result. Report those limitations rather than replacing absent measurements with zeros.

Agent action telemetry is another evidence stream. Microsoft documents querying the agent's Application Insights customEvents for tool executions, model calls, and approval decisions. These are not the workload's scenario traces. Use the agent's monitoring resource and its documented schema when auditing whether an investigation actually ran.

5. Applying the model to ten business risks

Every scenario on the reliability dashboard now has a component map, an illustrative three-panel dashboard, an investigation walkthrough, and report and KQL templates. The following matrix explains what the agent should establish and where this evaluation stops.

These constraints make the evaluation more useful, not less: an agent that identifies missing instrumentation is behaving more reliably than one that invents dependency failures, CPU percentages, or recovery events. Evaluate the quality of the uncertainty statement as carefully as the proposed mitigation.

6. Dashboards and Live Reports: three distinct surfaces

The public portal, the Azure Monitor workbook, and SRE Agent Live Reports serve related but different purposes. The portal is a custom HTML experience backed by selected Functions APIs. The workbook is an Azure Monitor visualization. Live Reports are saved operational views created within SRE Agent from its available connected data. A link or prompt does not create a report or grant access to a new source.

Each scenario's sample dashboard compares Before, Incident, and Recovered states. These are teaching values, not historical samples, predictions, or measured agent outcomes. Requested production panels such as message age, CPU percentage, or payment success must remain Not instrumented until an authorized source supplies them.

How to use this report workflow

  1. Open a scenario on the reliability dashboard and expand its Live Report template. Paste that template into the connected SRE Agent.
  2. Verify each panel against a real query. For queue backlog, show enqueue counts from traces separately from independently measured queue depth; leave message age unavailable if it is not collected.
  3. Save the report, run another bounded scenario, and select Reload. Inspect freshness and Agent consumption; do not fill missing panels with the portal's sample numbers.
Build a Live Report for the selected reliability scenario.
Scope: the connected rg-sre-demo resources, last 24 hours.
Include scenario trace counts, severity, latest status, and an evidence table.
Add operation-filtered request failure rate and P95 only from AppRequests.
Add queue or worker metrics only when a connected source actually exposes them.
Mark unavailable panels "Not instrumented"; do not use portal sample numbers.
Keep refresh connector-query-only; avoid model-assisted analysis on refresh.
Save the layout and verify it with a new scenario run and Reload.

Microsoft labels Live Reports as preview. The current guidance distinguishes creation and editing, which consume active-flow AAUs, from connector-only refreshes, which do not consume active-flow AAUs. Model-assisted refresh analysis does consume active-flow AAUs. That distinction is not a promise that the underlying Azure services or all report activity are free. Reports can also use cached connector results, so record freshness when presenting a time-sensitive investigation.

7. Identity, authorization, and approval are separate controls

The safest operating model does not rely on a prompt saying "be careful." It combines explicit resource scope, appropriate user roles, tool restrictions, review procedures, and independently inspectable audit records.

How to use these gates before enabling writes

Start with a read-only investigation. For configuration drift, have the agent propose the exact SRE_DEMO_MODE correction without applying it. Review the identity, target, effective policies, hooks, and automation run mode; authorize the change through your operational process. Then rerun config-drift to validate HTTP 200 and review the audit trail. Do not treat a request for approval as proof that every other tool is equally constrained.

  • User roles govern what a person can do with SRE Agent. Microsoft distinguishes Reader, Standard User, Author, and Administrator. An Azure subscription role should not be assumed to supply all SRE Agent data-plane capabilities.
  • Agent permissions govern the managed identity's access to Azure resources. Review effective roles and scope rather than inferring them from a friendly permission-level label. Microsoft's documented alert lifecycle integration includes subscription-level Monitoring Contributor requirements.
  • Run modes govern approval behavior for response plans and scheduled tasks, with an agent-level fallback. Set and verify the mode on the specific automation. Do not assume every newly created plan inherits the safety posture you intended.
  • Tool access policies add allow, ask, and deny decisions. Under the documented policy evaluation, an allow can bypass an ask; a globally denied tool cannot simply be enabled by a narrower allow.
  • Hooks add another governance layer. The tool-policy documentation describes user-defined hook allows that can override lower-level policy decisions, including a global deny. Treat hook authorship and configuration changes as privileged operations.

Review mode is not a universal "approve every side effect" switch. Microsoft's guidance distinguishes Azure infrastructure operations from other actions, and policy or hook decisions can change the approval path. Inspect the complete effective configuration, restrict write access, and test the actual tool workflow before connecting production.

For this evaluation, start with authorized read access and no automatic remediation. A proposed change should identify the exact command or tool arguments, its owner, expected impact, and rollback. Keep sensitive settings, message contents, and raw tool outputs out of the public portal. Workload data and connected documents are evidence to evaluate, not authority to override operational policy.

8. Extensibility: connect evidence before adding autonomy

The product overview describes skills, custom agents, Python tools, MCP servers, and hooks as extension points. Use them to close a specific operational gap rather than to expand the tool surface without a purpose. For example, a source repository connection can add release context; an observability connector can expose a missing dependency metric; a specialized workflow can constrain a repeatable diagnostic.

MCP exposes external capabilities as tools. Connecting a server therefore changes both what the agent can learn and what it may be able to do. Review the endpoint, credentials, returned data, individual tool permissions, and operational ownership. A read-only Azure identity does not automatically make an external connector read-only.

When to use specialized agents

Begin with one agent and the ten scenario prompts. Add a custom agent only when a repeated diagnostic needs distinct instructions, tools, or ownership. For example, a capacity specialist could compare memory, CPU, and queue signals once those measurements exist. Test it against the known simulation limits and preserve the same approval and evidence requirements; specialization does not supply missing telemetry or broader permissions.

None of the payment, retry, queue-consumer, or worker-profile gaps in the scenario catalog disappears because an agent supports extensions. Instrument or implement the missing system, connect it with authorized access, and then verify that the agent can retrieve its evidence. Only then evaluate whether a narrow, repeatable response is suitable for automation.

9. Cost engineering and evaluation lifecycle

Microsoft distinguishes always-on usage for an existing agent from active-flow usage for agent work. Token usage and model-specific rates influence active-flow consumption. Deleting a chat thread or simply leaving the agent idle is not the same as deleting the billable agent resource. Verify current pricing, eligibility, and regional availability before committing to an evaluation.

This repository's cost planner uses explicit planning assumptions: a new-customer trial for fixed charges, a 500-AAU active-flow allocation, supporting Azure spend, and a $100 monthly target. Those are evaluation assumptions, not a production price guarantee. Budget notifications are alerts, not a hard spending stop. A daily ingestion cap can also affect evidence availability and should not be treated as an infallible instantaneous cost ceiling.

The teardown workflow is scheduled before the intended trial boundary and has deletion permissions on the evaluation groups. Its success must be observed: check the workflow result and actual resource removal, and retain a manual cleanup owner. Do not rerun the full infrastructure deployment merely to publish a documentation update, because the deployment script computes a new teardown timestamp.

Authoritative billing model and current usage guidance: Pricing and billing [11]. Report-specific active-flow behavior: Live Reports usage and costs [7].

10. Evaluate evidence quality before promising autonomous recovery

Run a controlled, human-reviewed evaluation with the same incident questions used by your current responders. Record the start time, resources in scope, available telemetry, tools called, approvals, investigation output, and any performed action. Compare equivalent windows and instrumentation; an uninstrumented scenario is not a fair measure of root-cause accuracy.

MeasureEvidence to collectAcceptance approach
Time to useful evidenceElapsed time to the first cited observation that narrows the incidentCompare with a documented human baseline, not an invented percentage improvement.
Diagnostic qualityCorrect observations, supported hypotheses, counter-evidence, and explicit unknownsReject fabricated metrics and claims based solely on the simulation's root-cause label.
Governance correctnessEffective identities, tool decisions, approvals, and agent audit recordsVerify allowed diagnostics and blocked or reviewed write paths in the intended configuration.
Recovery validityCustomer-facing checks and before/after measurements for an actually performed changeDo not count sample charts, a healthy generic endpoint, or a release-marker edit as successful recovery.
Operational costActive-flow usage, underlying service spend, and evidence-retention costAgree a budget and cleanup owner before increasing automation or report frequency.

Adopt in stages: establish telemetry and read access; validate manual investigations; create stable reports; connect incident intake with explicit scope and review settings; then consider narrowly bounded automation with a tested rollback and a responsible owner. This sequence is an engineering recommendation for the evaluation, not a claim that production is safe by default.

The success criterion is a defensible operational decision: what happened, how the evidence supports it, what remains unknown, who may act, and how recovery will be verified. An agent that produces that record can reduce coordination friction without replacing service ownership.

  1. Register only the approved workload group with Reader access. Confirm the operational identity and effective RBAC scope.
  2. Connect code and workload logs, then upload reviewed knowledge. Verify actual queries and citations rather than relying on onboarding cards.
  3. Open Build + setup > Extensions > Skill builder > Create skill in the current preview UI. Microsoft Learn may call this Builder > Skills.

Skills, knowledge, and specialists are different

A skill is a reusable procedure with optional tools; the Agent loads relevant skills automatically. A knowledge file is searchable reference content without attached tools. A custom agent is an explicitly invoked specialist and can restrict accessible skills through allowed_skills. Adding a repository or committing a local skill file does not automatically deploy a native SRE Agent skill.

Start with a read-only evidence-triage procedure. A larger skill set can add queue assessment, configuration comparison, and report validation, but each needs an owner, a clear trigger, approved tools, and a tested evidence boundary. The service currently documents up to five concurrently active skills; this is not the same as the total number of enabled skills.

GitHub OAuth for the demo Agent remains pending. Incident intake remains optional and unconfigured. This guide does not enable autonomous response, grant new write permissions, or install skills automatically. Keep the existing Review-mode safeguards and teardown deadline.
